# 低干扰交互模式修复说明

基线：`48b44f8`（用户确认的初始版本）
分支：`fix/hot-menu-click`
改动：`shell/main.js` + `shell/preload.js`（共 189 行新增）

---

## 一、你报的两个症状，根因是什么

### 症状 ①：低干扰模式下菜单/设置面板点不动

面板 `.dshwv-menu` **不是**鲸鱼 `.dshwv-root` 的子节点，而是用
`document.body.appendChild()` 挂到 `body` 上的（挂件源码 `whale-widget.js`
第 11905 行 `dshwBodyAppend(menuBox)`）。

而初始版的 `interactiveRect()` **只扫 `.dshwv-root` 子树**：

```js
root = document.querySelector('.dshwv-root')
nodes = root.querySelectorAll('*')     // 面板根本不在这棵树里
```

面板用 `position:fixed` 定位，鲸鱼贴在屏幕右下角时它**必然向上展开**，
整体落在鲸鱼包围盒之外。热点窗只盖鲸鱼 → 面板那一片区域
**没有任何窗口接收鼠标** → 点不动。

实测几何（1707×1019 工作区）：

```
面板      y = 565 ~ 865
鲸鱼      y = 769 ~ 1019
热点窗    y = 755 ~ 1033     ← 面板顶部 190px 落在窗口之外
```

### 症状 ②：鼠标在鲸鱼上移动时光标在箭头 ⇄ 手型之间跳

`.dshwv-root` 带 CSS 过渡：

```css
.dshwv-root{ transition: left .16s ease, top .16s ease, transform .3s ease }
```

**过渡进行中 `getBoundingClientRect()` 返回的是插值位置**（正在移动中的坐标）。
初始版的 `applyHotRect()` 用「完全相等」判断要不要重新定位：

```js
if (prev.x === b.x && prev.y === b.y && prev.width === b.width && ...) return
```

于是每个 200ms 采样点都判定为"变了" → 每个采样点都调一次 `setBounds` 挪窗口。
**在光标正下方反复挪窗口**，系统会不断给热点窗补发进入/离开事件，
页面因此反复清掉又重建 hover 态 → 光标在 `grab`（手型）和默认箭头之间跳。

日志实证：`shell.log` 里有 **46 条**「热点窗定位」，`h` 在 147~156 之间来回摆。

## 二、改了什么

### `shell/main.js` —— 热点窗定位加阈值（提交 `e8a318a`）

把「完全相等」换成「位置/尺寸分别判 10px 阈值」，锚点是**上一次真正应用的**
`hotState.bounds`：

```js
const HOT_POS_EPS = 10
const HOT_SIZE_EPS = 10

const posSame  = |b.x - prev.x| <= 10 && |b.y - prev.y| <= 10
const sizeSame = |b.width - prev.width| <= 10 && |b.height - prev.height| <= 10
if (posSame && sizeSame) return          // 窗口一动不动
```

阈值取 10px 的依据：实测过渡抖动 ≤7px，真实变化是几百 px（菜单开合）
或几十 px（拖动），中间空档很大，10px 落在里面不会误伤。

**实测效果**（拿 `shell.log` 里真实的 46 条矩形序列回放）：

| | setBounds 次数 |
|---|---|
| 初始版 | 46 |
| 修复版 | 32（降 30%）|

被消掉的正是 `204x182 ⇄ 203x183` 这类 ±1~2px 抖动；
`282x269` / `274x483` 这类真实变化（菜单开合）**照常跟随**。

### `shell/preload.js` —— 并集逻辑重写（提交 `4fb2daf` + `8e3a5ec`）

**核心思路：几何即真相，单通路上报。**

| 新增函数 | 作用 |
|---|---|
| `rootBox(root)` | 鲸鱼落点盒 = 内联 `style.left/top`（**过渡目标值**，稳定）+ `offsetWidth/Height`（布局值，不受过渡影响）。**绝不读过渡中的 rect** |
| `insideRoot(el, root)` | 挂载点校验。专防「宽高写百分比、参照物却是视口」的事故（见下方 `.dshwv-pop`） |
| `relBoxOf(el, root, rb)` | 子树内元素的**落点盒**：取元素 rect 相对 root rect 的偏移 `dx/dy`，再套到 root 的落点盒上 ⇒ root 过渡时两者同步平移、`dx/dy` 不变；镜像也被 rect 自带 |
| `maskActiveNow(el)` | 遮罩激活判定 —— 只看**内联** `style.display` |
| `panelRect`/`popupRect(el)` | 面板：「只认 `display !== 'none'`；opacity 要求 `>= 0.9`（过渡中途 0.4 不算「开着」）」|
| `cardRect(el)` | 遮罩内卡片：先沿祖先链找到遮罩、查 `maskActiveNow` 放行，再取自己的可见矩形 |
| `hullFrac(img)` | 解析挂件写在 `.dshwv-img` 上的 `clip-path: polygon(x% y%, ...)`，取不透明像素凸包的包围盒比例 |
| `whaleBox(root, rb)` | 鲸鱼精确盒 = **图片盒 ∩ 凸包**（见 `三·再补`） |
| `popOpen(el, root)` | 气泡是否开着 —— 只看类名 `dshwv-pop-open` |
| `effectiveOpacity(el)` | 沿祖先链**累乘** opacity —— CSS opacity 不继承，子元素自身恒为 1，只看自身会把「父层已淡出」的层误判为可见 |
| `stabilizeRect(r)` | 页面侧死区（位移 6px / 尺寸 24px）|

`interactiveRect()` 现在是：
**① 鲸鱼精确盒 ∪ ② 开着的气泡 ∪ ③ 可见的 ☰ ∪ ④ 可见面板/菜单 ∪ ⑤ 遮罩内卡片**。
**既不扫 root 子树，也不并入遮罩本身。**

选择器拆成三类，语义互不污染：

| 类 | 内容 | 为什么 |
|---|---|---|
| `MASK_SEL` | 8 个遮罩（`cropmask`/`snapmask`/...）| **只用于判「父遮罩是否激活」**，本身不进并集 |
| `PANEL_SEL` | `menu`/`rolelist`/`qedit`/`usage-sub`/`tplhelp` 等 | 小尺寸、按需展开，几何直接进并集 |
| `CARD_SEL` | `cropwin`/`gifwin`/`bubcard`/`usage-card` 等 | 遮罩内的居中卡片，**这些才进并集** |
| `BUBBLE_SEL` / `MENU_BTN_SEL` | `pop` / `menu-btn` | 在 root **子树内**，走 `relBoxOf`，按类名/可见性放行 |

## 三·补、首次启动会抖一下（提交 `8e3a5ec` 定位 + `22c0e2a` 落地）

这是上一版修复后**残留的最后一个问题**。最终结论与最初设想不同，两个
提交分别承担「归因」和「解法」。

### 症状

启动 DSH 后**第一次**会抖，必须重新加载一次小鲸鱼挂件才正常 ——
**重载后一切正常**，且再怎么操作也不会复现。

### 尝试一（`8e3a5ec`）：遮罩的 CSS 默认值就是「可见」

8 个遮罩的 CSS 都长这样：

```css
.dshwv-cropmask{ position:fixed; inset:0; display:flex; ... }
                                    ↑ 铺满视口    ↑ 默认就是 flex，不是 none！
```

它们的显隐**完全靠内联 `style.display` 覆盖**（挂件源码里 73 处 `'none'`、
36 处 `'flex'`）。于是存在一个真实窗口期：

> 节点已创建 → CSS 的 `display:flex` 已生效 → **但内联 `display:none` 还没写进去**

此时 `getComputedStyle()` 读到的是 `'flex'`。上一版「只看 computed display」
的判定就把这个**尚未初始化**的遮罩当成「开着」，并集立刻被炸成整个视口。

日志实证（`h:455` 是面板并集的正确值）：

```
页面 {x:1462,y:565,w:246,h:455}   ← 面板并集（正确）
页面 {x:0,y:0,w:1708,h:1020}      ← 全视口！未初始化遮罩被误判
页面 {x:1462,y:565,w:246,h:455}   ← 立刻恢复
```

只有 `inset:0` 的遮罩能产生整视口矩形，所以来源确定无疑。

**为什么「重载一次就好」**：首次初始化是一大串 DOM 创建 + 逐个设内联 `none`，
这个窗口期真的会被 200ms 采样命中；重载后挂件重建很快、且已错过采样点。

### 修法（`8e3a5ec`）

1. **遮罩激活判定改看内联值**（`maskActiveNow`）。挂件对遮罩的内联值是**二值**的：
   - `'flex'` → 挂件主动打开的
   - `'none'` → 关闭
   - 空 → **还没轮到它初始化**，CSS 的 `flex` 只是兜底，不算开着

   这不依赖时序、零延迟，比「连续 N 次确认」更准（确认法会让真正打开的遮罩慢 600ms）。

2. **并集里不再并入遮罩本身，改为并入遮罩内的卡片**。
   把 `inset:0` 的遮罩并进来 = 把热点窗撑满全屏，那正是 `expanded` 老路的坑
   （全屏窗口 + 输入/focus 副作用）。而用户真正要点的是**遮罩里的卡片**
   （`cropwin` 320px、`bubcard` 440px、`usage-card` min(560px,92vw)…），
   尺寸居中，并集不会铺满视口。

3. **卡片的显隐由父遮罩决定**（`cardRect` 沿祖先链找遮罩 → 查 `maskActiveNow`）。
   这同时解掉了卡片「没有 `display:none`、常驻 DOM、自己无法判可见」的难题
   —— 也正是 `dec5364` 当初警告「别把 `*-win` 加进来」的原因。

### 验证（`8e3a5ec`）

新增场景断言（`_selftest/rect-union-test.js`，10 场景 39 断言全绿）：
- 内联 `display` 为空时，铺满视口的遮罩被忽略，并集 = **250×250**（旧逻辑会是 1707×1019）
- 遮罩打开时并的是**卡片**（1017×719 < 全视口），不是遮罩
- 首次启动 3 个采样周期并集全是 **250×250**

### 但实测：抖动仍在（`8e3a5ec` 未真正解决）

部署后用户实测反馈「**不行，并没有修复**」，首启仍会抖一次。
查日志（`run/shell.log`）确认新代码确实**已经**生效：

```
[2026-10-07T08:30:44.564Z] 热点窗定位 {"x":0,"y":0,"width":1707,"height":1034}
```

而 `shell.json` 显示 `startedAt: 2026-10-07T08:30:34.915Z` —— 启动时间在
部署**之后**，说明这次全视口定位来自新逻辑本身。

结论：这不只是「遮罩内联值」一个问题，而是**首启窗口期整体的一串 DOM
中间态**（900KB 脚本 + 几十个 body 节点逐个初始化）与 preload 200ms
采样的**时序竞争**。重载后挂件重建很快、DOM 生命周期更紧凑，采样就再也
命中不了。这类竞争难以穷举，继续深挖收益低。

### 解法（`22c0e2a`）：把「手动重载」自动化

既然「重载一次」是用户一直以来的操作、且**每次都能修好**，那就把它自动化：

```js
// shell/main.js —— did-finish-load 后延时重载一次
if (startupReloadDone) mark('reloaded')   // 重载后的第二次加载，正常路径
else scheduleStartupReload()              // 首启 → 安排一次重载
```

设计约束：

| 约束 | 实现 |
|---|---|
| **只重载一次**，绝不循环 | `startupReloadDone` 置位后 `scheduleStartupReload` 直接 return |
| 走**与手动完全相同**的路径 | `win.webContents.reload()`，与托盘「重新加载挂件」同一行调用 |
| 用户几乎无感 | 延时 `autoReloadDelayMs` 默认 **300ms** |
| 重载后热点窗不留在旧位置 | 重载前复位 `hotState.lastPageRect` / `bounds`，并向热点窗发 `mouseLeave` |
| 可关闭 | `config.json` 置 `"autoReloadOnStart": false` |
| 安全 | 窗口已销毁 / 为 `null` 时静默 return，不抛异常 |

**为什么是 300ms（原为 1500ms，后按实测调小）**：

初版取 1500ms 的思路是「等首启那一串初始化跑完再重载」。但实测下来
1500ms 太长 —— 用户能看出挂件「**闪一下**」。

改小到 300ms 反而更合理：重载时机的下限由 `did-finish-load` 保证
（那时页面已经 load 完），300ms 时**仍在跑的初始化会被直接中断重建**，
比「等它跑完再重载」更干净，用户也看不出那一闪。

### 验证（`22c0e2a` + 调延时的提交）

`_selftest/autoreload-test.js` —— **8 场景 24 断言全绿**：

- 默认 300ms；`autoReloadDelayMs` 可配；负数夹到 0
- ★ **只重载一次**（模拟重载后 `did-finish-load` 再次触发，总次数仍是 1）
- `autoReloadOnStart=false` 时不安排定时器，且日志说明原因
- 窗口销毁 / `win=null` 时安全退出
- 重载前 `hotState` 两处缓存均复位
- 源码级核对：托盘与自动路径都调用 `win.webContents.reload()`
- ★ **跨文件一致性**：`overlay.mjs` 的 `DEFAULT_CONFIG.autoReloadDelayMs`
  与 `main.js` 的 `?? 兜底值` 必须相等（这个值同时在两处，改一处漏一处
  会造成「配置里 300、实际 1500」这种极难查的问题）

## 三·再补、热点窗里约七成面积是死区（提交 `c310edd`）

前两轮把「抖动」和「点不动」都修掉了，但**基座一直是 `.dshwv-root` 的整块**。
顺着「热点窗到底是什么形状」往下查，发现基座本身取错了。

### 症状

在鲸鱼**旁边的空白处**点击，什么都没发生 —— 既点不到挂件，也**穿不到下面的浏览器/桌面**。

### 根因：root 是画布，不是鲸鱼

```css
.dshwv-root{position:fixed;right:0;bottom:0;--dshw-base:clamp(122px, ...);width:var(--dshw-base);height:var(--dshw-base);pointer-events:none;...}
.dshwv-body{position:absolute;left:0;top:0;width:100%;height:100%}
.dshwv-img {position:absolute;right:0;bottom:0;width:59.45%;height:59.45%;pointer-events:auto;object-fit:contain;object-position:right bottom}
```

DOM 是 `root(250×250)` → `body(100%)` → `img(59.45%)`。
**鲸鱼图片只占 root 的 59.45%（≈148.6px），还贴在右下角** —— 左上那一片是留给
气泡（`.dshwv-pop`，`width:100%;aspect-ratio:1026/700`）和 ☰ 按钮的**画布留白**。

而热点窗 `setIgnoreMouseEvents(false)` —— **从不忽略鼠标**，整块矩形都吃输入。
于是那七成留白里：鼠标被吃掉、那里什么都没画、点击也到不了下层窗口。

线上真实日志（17 条待机样本）算下来：

| | 热点窗 | 死区占比 |
|---|---|---|
| 旧（基座 = root） | 278×278 = 77,284px² | **71.4%** |
| 新（基座 = 图片盒） | 176.6×176.6 = 31,196px² | **29.2%** |

新版本残留的那 29% **全是 `hotPadding=14` 的刻意留边**（给气泡/菜单留余量、
吸收亚像素噪声），不是死区。

### 修法：三层收窄，每层都有回退

1. **基座从 root 换成 `.dshwv-img`**（`whaleBox`）。鲸鱼图片**右下角与 root 右下角重合**，
   所以贴边那一侧一个像素都没丢。
2. **再按挂件自己的凸包收一层**。挂件 v757（issue #147）起会给图片写
   `clip-path: polygon(x% y%, ...)` —— 那是它用命中图的**不透明像素凸包**算的
   （`buildHitClipPath`），也就是挂件自己认定「这里算鲸鱼」的边界。
   取它的包围盒 = 覆盖全部可点区域、一个多余像素都不带。
   拿不到（命中图加载失败 / 画布被抹白 → 挂件自己 `applyHitClip('')`）就退回图片盒 ——
   与挂件自己的 `whaleRectHit()` 回退分支**语义一致**。
   角色图不是正方形时这一层很关键：自带的 `DSH2.png` 是 **2048×1024**，
   按 `object-fit:contain` + `right bottom` 只画在盒子的**下半**，凸包直接把高度砍一半。
3. **几何一律走 `relBoxOf()`**（相对 root 落点盒），不读过渡中的 rect ——
   与 `rootBox` 同一个理由。

### 收窄带来的三个副作用，都处理了

| 副作用 | 处理 |
|---|---|
| **☰ 可能落到凸包之外**。非正方形角色图（2:1）只画在下半，而 ☰ 在图片盒的中上部 —— 漏了就是「菜单按钮点不动」 | 显式把 `.dshwv-menu-btn` 并入（可见时）。回归断言：不加它并集顶边是 944，加了是 874 |
| **气泡是能点的**。开着时挂件把 svg 的 `path/ellipse` 设成 `pointer-events:visiblePainted`，并且靠「点它」来关掉（`dismissWaitBubble`） | 开着时（类名 `dshwv-pop-open`）并入气泡盒。此时并集回到 root 整块 = **与今天行为一致，无回归** |
| **镜像**（`.dshwv-root.dshwv-left{transform:scaleX(-1)}`）会把图片从左翻到右，凸包要跟着翻 | 用图片 rect 相对 root rect 的 `dx` 反推：右对齐 ⇒ `dx≈宽-图宽`，镜像后 ⇒ `dx≈0`，取中点分界。**判错只影响凸包往哪半边映射**，最坏是没收到最紧，绝不会跑到鲸鱼反侧 |

### 顺手补漏：审计了所有 body 挂载节点

把挂件里 34 处 `dshwBodyAppend(...)` 的类名逐个解出来与清单比对：

- 遮罩 / 卡片 / 面板 **全部已覆盖** ✓
- 漏了 `.dshwv-tplhelp`（「?」说明圈 / 模板变量提示，`position:fixed`）—— **已补进 `PANEL_SEL`**。
  它自己没内容可点，但**点它会关**（挂件在 document 上监听 pointerdown），
  不并进来那次点击根本进不到页面
- `.dshwv-usagepanel` 是**死 CSS**（`usagePanel` 变量真实用的类是 `dshwv-usage-sub`，已在清单里），**不加**
- `.dshwv-pop` 虽然是 `width:100%`，但它挂在 `.dshwv-body` 里（不是 body 挂载），
  仍加了 `insideRoot` 挂载点校验兜底 —— 万一哪天改成直挂 body，那就是「整个视口宽」

### 验证

`_selftest/rect-union-test.js` —— **17 场景 66 断言全绿**（原 10 场景 39 断言）：

- ★ 并集 = 图片盒 `(1557,869) 150×150`，面积降到原来的 **36%**，右下角仍与 root 齐平
- ★ 凸包 `y[50%,100%]` ⇒ 并集高度 150 → **75**
- ★ px / 退化 / 非 `polygon` 的 clip-path **全部退回图片盒**（3 个畸形用例）
- ★ 非正方形角色图：☰ 被并进来（顶边 874 而非 944）；☰ 未显形/`hidden` 时不扩窗
- ★ 镜像：同一段凸包在未镜像时落 1557..1632、镜像后落 **1532..1607**
- ★ 气泡开/关：关着 150×150，开着 250×250
- ★ `.dshwv-pop` 若不在 root 子树里（事故模型：`width:100%` 参照物变成视口）
  ⇒ 挂载点校验直接判否，并集**没被全视口炸掉**
- ★ `relBoxOf`：root 与子元素 rect 同步过渡时，相对偏移不变（仍是 1557,869）
- 回归：场景 2（遮罩+卡片 1017×719）、场景 4（面板顶边 565 / 高 454）**数值完全不变**

`_selftest/hot-area-replay.js`（新增）用线上真实日志量化：死区 **71.4% → 29.2%**，
窗口面积 **−60%**。

## 三、两条已经走过的弯路（别再走）

1. **扫 `.dshwv-root` 整棵子树**
   子树里全是会动的装饰（呼吸动画、hover 悬浮、菜单按钮）。
   实测会把并集炸到 **1607×919 ≈ 整个视口**，而且每 200ms 都在变 → 窗口狂抖。

2. **只扫 root + 用 `expanded` 让路机制兜面板**
   抖动治好了，但面板点不动；更糟的是 `expanded` 是
   「本页先置位 → 主进程再扩窗」的两段式，**一旦主进程错过/拒绝扩窗**
   （拖动打断、`setBounds` 失败），本页 `reportRect` 就**永久让路** →
   热点窗永久停在旧位置 → **连鲸鱼都点不动**。

本次直接**取消 `expanded` 让路**，失败态从根上不存在。

- **凸包收窄**：`y[50%,100%]` ⇒ 高度 150 → 75；畸形 clip-path 全部退回图片盒
- **非正方形角色图**：☰ 必须被显式补回（顶边 874 而非 944）
- **镜像**：同一段凸包未镜像落 1557..1632、镜像落 1532..1607
- **气泡**：关着 150×150，开着 250×250；`.dshwv-pop` 不在 root 子树里 ⇒ 忽略
- **遮罩打开时并的是卡片**（1017×719 < 全视口），不是遮罩本身
- 未初始化的遮罩不再进并集（详见 `三·补` —— 单测通过，但**实测首启仍会抖**，
  故最终由 `22c0e2a` 的自动重载兜底）
